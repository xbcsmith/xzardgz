# Watcher / XZepr Integration: Phase 1 Integration Boundary

## Overview

This document is the Phase 1 design deliverable for the Watcher / XZepr
integration described in `docs/explanation/watcher_xzepr_integration_plan.md`.
Phase 1 is design-only: no Rust adapter code is written in this phase. Its
purpose is to resolve every ambiguity about field sourcing before Phase 2
implementation begins, so that the adapter can be written to a stable, reviewed
contract rather than against assumptions.

The integration boundary governs how an inbound `CloudEventMessage` received
from XZepr via Kafka is translated into the parameters required by
`WatcherExecutor::process_task`. `XzeprConsumer` is the sole Kafka consumption
mechanism; upstream producers publish XZepr-shaped `CloudEventMessage` payloads
to the task topic, and the adapter (written in Phase 2) translates those
messages into `WatcherTaskMessage` — the internal DTO — before handing off to
the executor. The results topic remains under xzardgz's own schema
(`WatcherResultMessage`) and is not governed by this document.

This document defines: which `CloudEventMessage.event_type` strings are
accepted; the exact field-by-field mapping from the XZepr envelope and
`EventEntity.payload` to `WatcherTaskMessage`; the `correlation_id` payload
contract that upstream producers must honor; and the conditions under which a
message is silently rejected without dispatching a workflow run. Every decision
recorded here constitutes a shared contract between xzardgz and the upstream
systems that produce XZepr events targeting this service.

## Allowed Event Types

Only two event type strings are accepted for task dispatch. Result event types
and all unknown strings are rejected.

| `CloudEventMessage.event_type` string | `WatcherEventType` variant | Dispatched as task | Derived plugin name |
| ------------------------------------- | -------------------------- | ------------------ | ------------------- |
| `xzardgz.technical_review.task`       | `TechnicalReviewTask`      | Yes                | `technical-review`  |
| `xzardgz.security_review.task`        | `SecurityReviewTask`       | Yes                | `security-review`   |
| `xzardgz.technical_review.result`     | `TechnicalReviewResult`    | No                 | n/a                 |
| `xzardgz.security_review.result`      | `SecurityReviewResult`     | No                 | n/a                 |
| Any other string                      | (none)                     | No                 | n/a                 |

Result event types are recognized by `WatcherEventType::from_event_str` but
carry `is_task() == false`; the adapter must reject them without dispatching a
workflow run and without logging a warning (they are well-formed events, just
not task events). Any unrecognized string returns `None` from `from_event_str`
and is rejected with a logged warning.

Plugin names are derived deterministically from the event type string. The
`plugin` field on `WatcherTaskMessage` is never taken from the payload; it is
always the value shown in the table above.

## CloudEventMessage to WatcherTaskMessage Field Mapping

The table below is the authoritative mapping for Phase 2 implementation. "Source
location" identifies which struct and field provides the value. "Payload key"
names the JSON key inside `EventEntity.payload` when the source is the opaque
payload blob.

| `WatcherTaskMessage` field | Source location                | Payload key           | Required | Default                        | Notes                                                                                                              |
| -------------------------- | ------------------------------ | --------------------- | -------- | ------------------------------ | ------------------------------------------------------------------------------------------------------------------ |
| `version`                  | Constant                       | n/a                   | n/a      | `"1"` (`WATCHER_TASK_VERSION`) | Always the constant; never from the message.                                                                       |
| `id`                       | Generated locally              | n/a                   | n/a      | Fresh ULID                     | Generated by the adapter at translation time; not taken from `CloudEventMessage.id`.                               |
| `spec_version`             | Constant                       | n/a                   | n/a      | `"1.0"`                        | Always the constant.                                                                                               |
| `event_type`               | `CloudEventMessage.event_type` | n/a                   | Yes      | n/a                            | Mapped via `WatcherEventType::from_event_str`; message rejected if not in the allow-list and `is_task()` is false. |
| `source`                   | `CloudEventMessage.source`     | n/a                   | Yes      | n/a                            | Copied verbatim from the envelope.                                                                                 |
| `repository`               | `EventEntity.payload`          | `repository`          | Yes      | n/a                            | Message rejected if missing or empty string.                                                                       |
| `target_branch`            | `EventEntity.payload`          | `target_branch`       | No       | `None`                         | Omitted from payload yields `None`; empty string is treated as `None`.                                             |
| `provider`                 | `EventEntity.payload`          | `provider`            | No       | `None`                         | Omitted from payload yields `None`.                                                                                |
| `model`                    | `EventEntity.payload`          | `model`               | No       | `None`                         | Omitted from payload yields `None`.                                                                                |
| `plugin`                   | Derived from `event_type`      | n/a                   | n/a      | See allow-list table           | Never taken from the payload; always derived.                                                                      |
| `plugin_config`            | `EventEntity.payload`          | `plugin_config`       | No       | `serde_json::Value::Null`      | Passed opaquely to the plugin.                                                                                     |
| `dry_run`                  | `EventEntity.payload`          | `dry_run`             | No       | `false`                        | Boolean; missing key treated as `false`.                                                                           |
| `workspace_directory`      | `EventEntity.payload`          | `workspace_directory` | No       | `None`                         | Omitted from payload yields `None`.                                                                                |
| `metadata`                 | `EventEntity.payload`          | `metadata`            | No       | `{}`                           | Object with string values; missing key yields empty map.                                                           |
| `requested_report_formats` | `EventEntity.payload`          | `report_formats`      | No       | `[]`                           | Array of strings; missing key yields empty vec.                                                                    |
| `correlation_id`           | `EventEntity.payload`          | `correlation_id`      | Yes      | n/a                            | Message rejected if missing or empty string. See dedicated section.                                                |
| `reply_topic_override`     | `EventEntity.payload`          | `reply_topic`         | No       | `None`                         | Omitted from payload yields `None`.                                                                                |

Fields from `CloudEventMessage` that are **not** mapped to `WatcherTaskMessage`
and are intentionally discarded by the adapter:

- `CloudEventMessage.id` — XZepr-assigned ULID for the event envelope; not
  usable as a `correlation_id`.
- `CloudEventMessage.success` — XZepr delivery flag; not relevant to task
  dispatch.
- `CloudEventMessage.specversion` — CloudEvents version; consumed implicitly by
  deserialization.
- `CloudEventMessage.api_version`, `.name`, `.version`, `.release`,
  `.platform_id`, `.package` — XZepr metadata; not needed by the executor.
- `EventEntity.id` — XZepr entity ID; not usable as a `correlation_id`.
- `EventEntity.event_receiver_id` — XZepr routing concept; not consulted.
- `EventEntity.name`, `.version`, `.release`, `.platform_id`, `.package`,
  `.description`, `.success`, `.created_at` — XZepr entity metadata; not needed
  by the executor.

## EventEntity.payload Schema

`EventEntity.payload` is an opaque `serde_json::Value` from xzardgz's
perspective. The adapter extracts the following keys. This section is written as
a reference for upstream XZepr producers.

| Key                   | JSON type        | Required | Description                                                                                      |
| --------------------- | ---------------- | -------- | ------------------------------------------------------------------------------------------------ |
| `correlation_id`      | string           | Yes      | Non-empty string identifying this workflow run. ULID strongly recommended.                       |
| `repository`          | string           | Yes      | URL or identifier of the repository to analyze. Must be non-empty.                               |
| `target_branch`       | string           | No       | Branch to check out and analyze. Omit or set to `null` to use the repository default branch.     |
| `provider`            | string           | No       | AI provider override (e.g. `"openai"`, `"anthropic"`). Omit to use the global config.            |
| `model`               | string           | No       | Model override (e.g. `"gpt-4o"`). Omit to use the global config.                                 |
| `plugin_config`       | object           | No       | Plugin-specific configuration object, passed opaquely to the plugin.                             |
| `dry_run`             | boolean          | No       | When `true`, the run makes no AI calls and writes no output. Defaults to `false`.                |
| `workspace_directory` | string           | No       | Workspace root override. Omit to use the global config.                                          |
| `metadata`            | object           | No       | Flat string-to-string map of arbitrary metadata. Passed through to the result.                   |
| `report_formats`      | array of strings | No       | Report format names to produce (e.g. `["markdown", "json"]`). Omit for plugin defaults.          |
| `reply_topic`         | string           | No       | Kafka topic override for publishing the result message. Omit to use the configured result topic. |

All other keys in `EventEntity.payload` are ignored by the adapter.

A minimal valid payload example:

```json
{
  "correlation_id": "01JXXXXXXXXXXXXXXXXXXXXXXX",
  "repository": "https://github.com/example/myrepo"
}
```

A fully populated payload example:

```json
{
  "correlation_id": "01JXXXXXXXXXXXXXXXXXXXXXXX",
  "repository": "https://github.com/example/myrepo",
  "target_branch": "main",
  "provider": "openai",
  "model": "gpt-4o",
  "dry_run": false,
  "workspace_directory": "/tmp/xzardgz-workspaces",
  "metadata": {
    "team": "platform",
    "ticket": "ENG-1234"
  },
  "report_formats": ["markdown", "json"],
  "plugin_config": {},
  "reply_topic": "xzardgz.results.team-platform"
}
```

## correlation_id Specification

### Exact payload key name

The key is `correlation_id` (lowercase, underscore-separated). There is no
acceptable variant spelling. The key must appear inside `EventEntity.payload`;
it must not be taken from any other location.

### Why correlation_id lives in the payload, not the XZepr envelope

`CloudEventMessage` carries several identifiers at the envelope level:
`CloudEventMessage.id` (XZepr's own ULID for the event), `EventEntity.id`
(XZepr's entity record ID), and `EventEntity.event_receiver_id` (an XZepr
routing concept). None of these are usable as a `correlation_id` for two
reasons:

1. XZepr assigns them; xzardgz cannot control or predict their values.
2. Modifying XZepr to add an envelope-level field is out of scope. XZepr is an
   independent service, and this integration must not require any changes on the
   XZepr side.

`EventEntity.payload` is the producer-defined JSON blob. The upstream system
that creates and publishes the XZepr event already controls this blob's content
entirely, so placing `correlation_id` there requires only a change to the
upstream producer — not to XZepr itself.

### Required for dispatch

`correlation_id` is a required field. A message where
`EventEntity.payload["correlation_id"]` is absent, set to `null`, or is an empty
string is rejected. No `WatcherTaskMessage` is constructed, no
`WatcherExecutor::process_task` call is made, and no workflow run is dispatched.
The rejection is logged as a warning with enough context to identify the
offending message (at minimum: the `CloudEventMessage.id` and `event_type`).

### Recommended format

Any non-empty string is accepted. A ULID (Universally Unique Lexicographically
Sortable Identifier) is strongly recommended for upstream producers because
ULIDs are:

- Globally unique without coordination.
- Lexicographically sortable by generation time, making log correlation
  straightforward.
- Already the format used by xzardgz and XZepr for their own internal IDs.

Example ULID: `01JXXXXXXXXXXXXXXXXXXXXXXX`

### What happens when correlation_id is missing

The message is rejected at the adapter boundary before any workflow run is
started. The Kafka offset is still committed so the message is not reprocessed.
A warning is emitted to the structured log including the `CloudEventMessage.id`
and `event_type`. No result message is published to the result topic.

### No XZepr-side change required

The `correlation_id` contract is entirely between xzardgz and the upstream
producer that populates `EventEntity.payload`. XZepr treats `payload` as an
opaque blob and passes it through without inspection. No modification to the
XZepr service, its schema, or its event receiver configuration is needed to
adopt this contract.

## event_receivers and event_receiver_groups

`CloudEventData.event_receivers` and `CloudEventData.event_receiver_groups` are
explicitly ignored for dispatch purposes. The adapter never reads these arrays.

These arrays are XZepr-specific routing and registration concepts. An
`EventReceiverEntity` describes a registered subscriber and its accepted schema;
an `EventReceiverGroupEntity` describes a set of receivers that share a
triggering condition. Neither concept has an equivalent in xzardgz's execution
model: xzardgz does not use XZepr's receiver registration to decide what to run
or where to send results. Dispatch is determined solely by the
`CloudEventMessage.event_type` string and the fields inside
`EventEntity.payload`.

Both arrays are reserved for potential future use — for example, a future phase
might read `event_receiver_groups` to support fan-out dispatch or multi-target
result routing. No such use is planned or implied by this document. For now,
they are deserialized by the `CloudEventData` struct (to avoid deserialization
errors if they are present) and then discarded.

## Message Selection: data.events[0]

The adapter reads exactly one `EventEntity` per `CloudEventMessage`: the first
element of `CloudEventData.events`, i.e. `data.events[0]`. All payload field
extraction (`repository`, `correlation_id`, etc.) is performed against this
single entity.

If `data.events` is empty, the message is rejected: no `WatcherTaskMessage` is
constructed, no workflow run is dispatched, and the rejection is logged as a
warning. The Kafka offset is still committed.

Messages where `data.events` has more than one element are accepted; elements
beyond index 0 are ignored. There is no fan-out on multiple events within a
single `CloudEventMessage` in Phase 2. Multi-event fan-out is deferred to a
later phase.

The choice to use only `data.events[0]` reflects the current upstream producer
behavior: all known XZepr producers targeting xzardgz publish exactly one
`EventEntity` per message. This assumption will be revisited if multi-entity
messages become a production requirement.

## Kafka Configuration Reconciliation (Phase 2 Preview)

Two separate Kafka configuration surfaces exist in the codebase today:

- `KafkaConfig` and `TopicsConfig` in `src/config.rs`: operator-facing YAML
  configuration, deserialized from `config.yaml` via serde. `KafkaConfig`
  carries broker addresses, group ID, security protocol, SASL mechanism, SASL
  credential environment variable names, and SSL CA location. `TopicsConfig`
  carries the task topic name (default `xzardgz.tasks`) and the result topic
  name (default `xzardgz.results`). These are the fields operators configure in
  `config.example.yaml`.

- `KafkaConsumerConfig` in `src/xzepr/consumer/config.rs`: a runtime struct
  built from environment variables (via `KafkaConsumerConfig::from_env`) and
  used directly by `XzeprConsumer` when constructing its `StreamConsumer`. It is
  not serde-serializable and has no connection to `config.yaml`.

Phase 2 will introduce a translation layer that builds a `KafkaConsumerConfig`
from the operator-supplied `KafkaConfig` and `TopicsConfig`, so operators
configure Kafka once in `config.yaml` and the runtime consumer is automatically
consistent with that configuration. Environment variable overrides may be
preserved for deployment environments where secrets must not appear in
configuration files.

## Rejection Rules

A `CloudEventMessage` is rejected — no `WatcherTaskMessage` is constructed and
no workflow run is dispatched — under any of the following conditions:

1. `CloudEventMessage.event_type` is not in the allowed event type list (i.e.
   `WatcherEventType::from_event_str` returns `None`).
2. `CloudEventMessage.event_type` maps to a result variant
   (`TechnicalReviewResult` or `SecurityReviewResult`), i.e.
   `WatcherEventType::is_task()` returns `false`.
3. `CloudEventData.events` is empty.
4. `EventEntity.payload["correlation_id"]` is absent, null, or an empty string.
5. `EventEntity.payload["repository"]` is absent, null, or an empty string.
6. `WatcherMatcher` does not match: the event type, repository, plugin,
   platform, or metadata filters configured in `MatcherConfig` exclude this
   message.

Conditions 1, 3, 4, and 5 are logged as warnings. Condition 2 is not logged as a
warning (result events are normal traffic, not errors). Condition 6 uses the
existing `WatcherMatcher` logging behavior. In all cases the Kafka offset is
committed so the message is not reprocessed on the next poll.

## Success Criteria

Phase 1 is complete when the following conditions are met:

- No ambiguity remains about which `CloudEventMessage` field or
  `EventEntity.payload` key populates each parameter of
  `WatcherExecutor::process_task` before Phase 2 implementation begins. The
  field-mapping table in this document is the single source of truth for that
  mapping.
- The `correlation_id` payload key name is documented and agreed upon, so
  upstream producers publishing through XZepr can adopt it without requiring any
  change to XZepr itself.
- The decision to ignore `event_receivers` and `event_receiver_groups` for
  dispatch is explicitly recorded.
- The `data.events[0]` selection rule and its rejection behavior for empty
  events arrays are explicitly recorded.
- The Phase 2 Kafka configuration reconciliation work is scoped and described at
  a level sufficient to begin implementation.
